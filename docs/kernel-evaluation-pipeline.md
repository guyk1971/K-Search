# Kernel Evaluation Pipeline

This document explains the exact process K-Search uses to evaluate a generated GPU kernel — from raw code to a final `EvalResult` with correctness status and performance score.

---

## 1. High-Level Flow

```
LLM generates code
        │
        ▼
┌─────────────────┐
│  Solution object │   (code + build spec + language + entry point)
└────────┬────────┘
         │
         ▼
┌─────────────────────┐
│  Task.run_benchmark()│   (dispatches to local or remote evaluator)
└────────┬────────────┘
         │
    ┌────┴─────┐
    │          │
    ▼          ▼
 LOCAL      REMOTE (CudaGym)
    │          │
    ▼          ▼
┌──────────────────┐
│ Phase 1: TESTS   │   correctness check (fail-fast)
│ Phase 2: BENCH   │   performance timing (only if tests pass)
│ Phase 3: PROFILE │   optional profiling (only if bench passes)
└────────┬─────────┘
         │
         ▼
┌─────────────────┐
│   EvalResult     │   (status, latency_ms, score, metrics, log_excerpt)
└─────────────────┘
```

---

## 2. The Solution Object

**Input to evaluation.** Generated by the kernel generator after LLM produces code.

```python
# k_search/tasks/task_base.py:188
@dataclass
class Solution:
    name: str                  # e.g. "gpt-5_gpumode_trimul_triton_r3"
    definition: str            # task name
    author: str                # model name
    spec: BuildSpec            # language, target_hardware, entry_point
    sources: list[SourceFile]  # [{path: "submission.py", content: "..."}]
```

For **Triton/Python** tasks: a single `submission.py` file with a `custom_kernel()` function.

For **CUDA** tasks: three files — `kernel.h`, `kernel.cu`, `main.cpp` — which get wrapped into a `submission.py` via `cuda_sources_to_submission_py()` (using PyTorch `load_inline`).


### `tests` vs `benchmarks` — What Each Means

| Aspect | `tests` | `benchmarks` |
|--------|---------|-------------|
| **Purpose** | Functional correctness validation | Performance measurement |
| **Gate** | Must ALL pass before benchmarks run | Only runs if tests pass |
| **Timing** | No timing — only correctness check | `torch.cuda.Event` precision timing |
| **Count** | Many (18 for TriMul) — stress-test edge cases | Multiple (7 for TriMul) — diverse representative workloads |
| **Distributions** | Both `normal` and `cauchy` (tests numerical stability) | Both `normal` and `cauchy` |
| **Shapes** | Varied (32→1024 seqlen, with/without mask) | Varied (256→1024 seqlen, different dims, with/without mask) |
| **On failure** | Fail-fast: first failure stops evaluation | Must also pass correctness before timing |

**Key insight:** Tests sweep a wide range of shapes, seeds, and distributions to catch correctness regressions. Benchmarks use **multiple representative workloads** spanning different sequence lengths (256–1024), dimensions (128, 384), batch sizes (1–2), and distributions (normal, cauchy) to ensure the kernel performs well across the full operating range. The final score is the **geometric mean** of all benchmark latencies, so a kernel that is fast on one shape but slow on another will be penalized.

## 5. Phase 1: Functional Correctness (Tests)

### 5.1 The Evaluation Harness

The GPUMode evaluator runs inside a temporary directory. Files from `task.yml` are materialized on disk, with `@SUBMISSION@` replaced by the generated code.

```python
# k_search/tasks/gpu_mode/libkernelbot/run_eval.py:853
def run_config(config: dict):
    # Build system info, serialize test/benchmark specs
    # For Python: run_pytorch_script(sources, main="eval.py", mode="benchmark", ...)
    # For CUDA: compile first, then run_single_evaluation(["./eval.out"], ...)
```

The actual evaluation is driven by `eval.py` (vendored from GPUMode), which is invoked as a subprocess:

```bash
python3 eval.py benchmark tests.txt
```

Communication between the harness and `eval.py` happens via a **POPCORN pipe** — a dedicated file descriptor where structured key-value results are written (not stdout, to avoid pollution from user code).

### 5.2 How Correctness Is Checked

For each test spec, the evaluator:

1. **Generates input** using `generate_input(**test_args)` with the spec's seed, shape, and distribution
2. **Runs the submission** `custom_kernel(data)` in a spawned multiprocessing pool (isolation)
3. **Compares output** against reference implementation

```python
# k_search/tasks/gpu_mode/trimul/reference.py:123
check_implementation = make_match_reference(ref_kernel, rtol=2e-2, atol=2e-2)
```

The comparison uses `verbose_allclose`:

```python
# k_search/tasks/gpu_mode/trimul/utils.py:30-68
def verbose_allclose(received, expected, rtol=1e-05, atol=1e-08, max_print=5):
    diff = torch.abs(received.float32 - expected.float32)
    tolerance = atol + rtol * torch.abs(expected)
    tol_mismatched = diff > tolerance
    # Also checks NaN/Inf mismatches
    nan_mismatched = torch.logical_xor(torch.isnan(received), torch.isnan(expected))
    # ...
```

**Tolerance for TriMul:** `rtol=2e-2, atol=2e-2` (2% relative + 2% absolute). This is generous because optimized kernels may use different floating-point reduction orders, TF32, or fused operations that shift results slightly.

The reference kernel (`ref_kernel`) runs the canonical PyTorch implementation with `CuDNN TF32 disabled` and `deterministic=True` to produce a stable baseline:

```python
# k_search/tasks/gpu_mode/trimul/reference.py:51

    with DisableCuDNNTF32():
        # ... canonical PyTorch TriMul implementation
```

### 5.3 Test Phase Flow

```python
# k_search/tasks/gpu_mode/trimul/eval.py:151-171
def run_testing(logger, pool, tests):
    for idx, test in enumerate(tests):
        good, message = run_single_test(pool, test)
        if not good:
            logger.log(f"test.{idx}.status", "fail")
            logger.log(f"test.{idx}.error", message)

```

**Important:** All 18 tests are run (no early exit on failure within the test phase). The overall `check` is `pass` only if every test passes.

## 6. Phase 2: Performance Benchmarking

### 6.1 Timing Method

Benchmarks use **CUDA events** for GPU-accurate timing:

```python
# k_search/tasks/gpu_mode/trimul/eval.py:174-215
def _run_single_benchmark(test, recheck, max_repeats=100, max_time_ns=10e9):
    data = generate_input(**test.args)

    # Pre-check: verify correctness before timing
    output = custom_kernel(data)
    good, message = wrap_check_implementation(check_copy, output)
    if not good:
        return message  # Fail: don't even time an incorrect kernel

    # Timing loop
    for i in range(max_repeats):
        torch.cuda.synchronize()
        start_event = torch.cuda.Event(enable_timing=True)
        end_event = torch.cuda.Event(enable_timing=True)

        start_event.record()
        output = custom_kernel(data)
        end_event.record()
        torch.cuda.synchronize()

        duration_ns = start_event.elapsed_time(end_event) * 1e6  # ms → ns
        durations.append(duration_ns)

        # Early-stop conditions (after ≥2 iterations):
        if i > 1:
            stats = calculate_stats(durations)
            if stats.err / stats.mean < 0.001:     # <0.1% relative error → converged
                break
            if stats.mean * stats.runs > max_time_ns: # >10s total → budget exceeded
                break
            if total_time > 120e9:                   # >120s wall-clock → hard stop
                break

    return calculate_stats(durations)  # Stats(runs, mean, std, err, best, worst)
```

**Key timing details:**
- **Instrument:** `torch.cuda.Event(enable_timing=True)` — measures GPU-side execution time, not CPU wall clock
- **Synchronization:** `torch.cuda.synchronize()` before start and after end to ensure accurate event timing
- **Max iterations:** 100 per benchmark spec
- **Convergence criterion:** Standard error < 0.1% of mean
- **Time budget:** 10 seconds total GPU time OR 120 seconds wall-clock
- **Warmup:** One dummy benchmark run before the real timing loop (`run_benchmarking` line 223)

### 6.2 Statistics

```python
# k_search/tasks/gpu_mode/trimul/eval.py:102-113
@dataclass
class Stats:
    runs: int     # number of timed iterations
    mean: float   # mean duration (ns)
    std: float    # standard deviation
    err: float    # standard error = std / sqrt(runs)
    best: float   # min duration
    worst: float  # max duration
```

### 6.3 Benchmark Flow

```python
# k_search/tasks/gpu_mode/trimul/eval.py:222-239
def run_benchmarking(logger, pool, tests):
    # Warmup run (not recorded)
    run_single_benchmark(pool, tests[0], False, 100, 10e7)

    for idx, test in enumerate(tests):
        result = run_single_benchmark(pool, test, False, 100, 10e9)
        if isinstance(result, Stats):
            # Log all stats: runs, mean, std, err, best, worst
            for field in dataclasses.fields(Stats):
                logger.log(f"benchmark.{idx}.{field.name}", getattr(result, field.name))
        else:
            # result is an error message (correctness failure)
            logger.log(f"benchmark.{idx}.status", "fail")
            logger.log(f"benchmark.{idx}.error", result)
```

### 6.4 Aggregation Across Benchmarks

When `task.yml` defines multiple benchmark specs, results are aggregated via the `ranking_by` policy:

```python
# k_search/tasks/gpu_mode/evaluator.py:63-77
def _aggregate_score_s(means_s, ranking_by):
    if ranking_by == "last":   return means_s[-1]           # only last benchmark
    if ranking_by == "mean":   return sum(means_s) / len    # arithmetic mean
    if ranking_by == "geom":   return prod(means_s)**(1/n)  # geometric mean
```

**TriMul uses `ranking_by: "geom"`** (geometric mean) across all 7 benchmark specs. This means the reported latency is:

```
latency = (mean_0 × mean_1 × mean_2 × ... × mean_6) ^ (1/7)
```

This penalizes kernels that are fast on some shapes but regress on others — a kernel must perform consistently well across all 7 workloads to achieve a good score.

The per-benchmark `mean` values (in nanoseconds from `eval.py`) are:
1. Extracted from the POPCORN pipe results as `benchmark.{i}.mean` for i=0..6 (ns)
2. Converted to seconds
3. Aggregated via geometric mean
4. Converted to milliseconds for the final `EvalResult.latency_ms`

```python
# k_search/tasks/gpu_mode/evaluator.py:46-60
def _extract_benchmark_means_s(run_result_dict):
    n = int(run_result_dict["benchmark-count"])
    for i in range(n):
        mean_ns = float(run_result_dict[f"benchmark.{i}.mean"])
        means_s.append(mean_ns / 1e9)  # ns → seconds
```

## 7. Evaluation Modes

### 7.1 GPUMode Submission Modes

The GPUMode harness supports several modes (`k_search/tasks/gpu_mode/libkernelbot/consts.py:82-100`):

| Mode | What It Does |
|------|-------------|
| `test` | Run all test specs, report pass/fail per test. No timing. |
| `benchmark` | Run all benchmark specs with timing. Each spec is correctness-checked first. |
| `profile` | Run benchmark specs under `torch.profiler` (CPU + CUDA activities). No correctness gate. |
| `leaderboard` | Run tests first (fail-fast); if passed, run benchmarks with `recheck=True` (re-verify correctness on each timed iteration with perturbed seeds). |
| `private` | Like `leaderboard` but with secret seed and limited feedback. |

**K-Search default:** `benchmark` mode (correctness is checked per-benchmark-spec before timing, but not re-checked on every iteration).

**Leaderboard mode** is stricter: it re-generates input with perturbed seeds on each timing iteration and re-checks correctness, preventing kernels that "cheat" by caching or hardcoding outputs.

### 7.2 The `ranking_by` Aggregation Options

Defined in `k_search/tasks/gpu_mode/libkernelbot/consts.py:108-111`:

| Policy | Behavior | Use Case |
|--------|----------|----------|
| `last` | Only the last benchmark spec matters | Single representative workload |
| `mean` | Arithmetic mean of all benchmark means | Equal weight to all workloads |
| `geom` | Geometric mean of all benchmark means | Penalizes outlier regressions |

In `run_single_evaluation`, the `ranking_by` policy also affects which benchmark specs are actually run:

```python
# k_search/tasks/gpu_mode/libkernelbot/run_eval.py:577-580
if ranking_by == "last":
    cases.write(benchmarks.splitlines(keepends=True)[-1])  # only run last spec
else:
    cases.write(benchmarks)  # run all specs
```

## 8. The EvalResult

The final output of evaluation. Task-agnostic so generators work with both GPUMode and FlashInfer.

```python
# k_search/tasks/task_base.py:18-31
@dataclass
class EvalResult:
    status: str                              # "passed", "failed", "compile_error", "runtime_error"
    latency_ms: float | None                 # aggregate latency (lower is better)
    reference_latency_ms: float | None       # baseline comparison (FlashInfer)
    mean_vs_baseline_factor: float | None    # speedup vs baseline (>1 is better; FlashInfer)
    speedup_factor: float | None             # alternative speedup metric
    log_excerpt: str                         # error logs (empty on pass)
    metrics: dict[str, Any]                  # task-specific: score_name, score, profiling data, etc.
```

### 8.1 Scoring Hierarchy

`EvalResult.score()` returns a comparable scalar (higher = better):

```python
# k_search/tasks/task_base.py:103-131
def score(self):
    # 1. Task-defined score (e.g. GPUMode's 1/latency_ms)
    if metrics["score"] is a number:  return metrics["score"]

    # 2. Baseline comparison (FlashInfer)
    if passed and mean_vs_baseline_factor > 0:  return mean_vs_baseline_factor

    # 3. Speedup factor
    if passed and speedup_factor > 0:  return speedup_factor

    # 4. Inverse latency (last resort)
    if passed and latency_ms > 0:  return 1.0 / latency_ms

    # 5. Failure
    return -1.0
```

### 8.2 GPUMode Score Construction

```python
# k_search/tasks/gpu_mode_task.py:374-403
# score = 1.0 / latency_ms  (inverse millisecond latency)
metrics = {
    "score_name": "inv_latency_ms",
    "score": 1.0 / latency_ms,   # higher = faster kernel = better
    "gpumode_mode": "benchmark",
    "gpumode_run_key": "benchmark",
    "gpumode_run_success": True,
    "gpumode_run_passed": True,
}
```

### 8.3 FlashInfer Score Construction

FlashInfer evaluates across multiple workloads and computes:
- `speedup_factor`: speedup vs reference implementation per workload
- `mean_vs_baseline_factor`: speedup vs a named baseline solution (if configured)
- `latency_ms`: mean latency across workloads

FlashInfer eval config provides fine-grained control:
```python
FlashInferBenchEvalConfig(
    warmup_runs=10,    # GPU warmup iterations (not timed)
    iterations=50,     # timed iterations per trial
    num_trials=3,      # independent trial runs
    rtol=1e-2,         # correctness tolerance (relative)
    atol=1e-2,         # correctness tolerance (absolute)
)
```

## 9. Local vs Remote (CudaGym) Evaluation

### 9.1 Local Evaluation

The default path. Evaluation runs on the same machine as K-Search.

```
Solution → evaluate_trimul_submission() → libkernelbot harness
    ├─ Creates temp directory, writes files
    ├─ For Python: python3 eval.py benchmark tests.txt (subprocess)
    ├─ For CUDA: nvcc compile → ./eval.out benchmark tests.txt (subprocess)
    └─ Reads POPCORN pipe for structured results → GpuModeEvalSummary → EvalResult
```

**Requirements:** Local GPU, CUDA toolkit, PyTorch.

### 9.2 Remote Evaluation (CudaGym)

Enabled with `--eval-backend cudagym --cudagym-url <URL>`.

```
Solution → build_remote_eval_package() → RemoteEvaluator.evaluate(package)
    │
    ├─ Package contains:
    │   - submission.py (generated kernel)
    │   - driver.py (self-contained: reference impl + input generator + correctness checker + timing loop)
    │   - run_command: "python3 driver.py"
    │
    ├─ Step 1: Compile (CUDA only; skipped for Triton/Python)
    │   → CudaGymClient.compile(CompilationRequest)
    │
    ├─ Step 2: Execute
    │   → CudaGymClient.execute(ExecutionRequest)
    │   → driver.py runs tests + benchmarks, prints JSON result between markers
    │
    ├─ Step 3: Profile (optional, if execution passed)
    │   → CudaGymClient.profile(ProfilingRequest)
    │   → NCU + nsys profiling data
    │
    └─ parse_driver_output(stdout) → EvalResult
```

**Code:** `k_search/eval/remote_evaluator.py`

**Key difference:** The remote driver is fully self-contained — it embeds the reference implementation, input generator, and correctness checker so no K-Search code is needed on the remote server.

| Aspect | Local | Remote (CudaGym) |
|--------|-------|-------------------|
| GPU required on host | Yes | No (only on server) |
| Compilation | Local nvcc / PyTorch JIT | Async HTTP to CudaGym compile server |
| Execution | subprocess in temp dir | CudaGym execute server |
| Profiling | `torch.profiler` | NCU + nsys via CudaGym |
| Timeout | Per-mode from task.yml | Per-step: compile (120s), execute (300s), profile (150s) |
| Dependencies | Full CUDA stack + PyTorch | Only `cudagym` client library |

## 10. End-to-End Example: TriMul Benchmark Evaluation

Given a Triton submission that defines `custom_kernel(data)`:

1. **Solution created** with `submission.py` containing the kernel code
2. **`GpuModeTriMulTask.run_benchmark()`** called
3. **`evaluate_trimul_submission()`** invoked with `mode="benchmark"`
4. **`task.yml` loaded** → `LeaderboardTask` with 18 tests + 7 benchmarks
5. **`run_config(config)`** builds the execution environment:
   - Writes `submission.py`, `eval.py`, `reference.py`, `utils.py`, `task.py` to temp dir
   - Runs `python3 eval.py benchmark benchmarks.txt` as subprocess
6. **Inside `eval.py`:**
   - **Warmup:** 1 dummy benchmark run on the first spec (100 iters, 100ms budget)
   - **For each of the 7 benchmark specs:**
     - Generate input: e.g. `generate_input(seqlen=256, bs=2, dim=128, hiddendim=128, seed=9371, nomask=True, distribution="normal")`
     - **Correctness pre-check:** `custom_kernel(data)` → `check_implementation(data, output)` with `rtol=2e-2, atol=2e-2`
     - If incorrect → fail immediately, no timing for this spec
     - **Timing loop** (up to 100 iterations):
       - `torch.cuda.synchronize()`
       - Record start CUDA event
       - `custom_kernel(data)`
       - Record end CUDA event
       - `torch.cuda.synchronize()`
       - `duration_ns = start.elapsed_time(end) * 1e6`
       - Check convergence: stop if std_error/mean < 0.1%
     - Compute `Stats(runs, mean, std, err, best, worst)` in nanoseconds
   - Write results to POPCORN pipe: `benchmark.0.mean`, `benchmark.1.mean`, ... `benchmark.6.mean`
7. **Results extracted and aggregated:**
   - 7 per-benchmark means (ns) → converted to seconds: `[m0, m1, m2, m3, m4, m5, m6]`
   - Geometric mean: `aggregated_s = (m0 × m1 × m2 × m3 × m4 × m5 × m6) ^ (1/7)`
   - `latency_ms = aggregated_s * 1000.0`
8. **EvalResult constructed:**
   - `status = "passed"`
   - `latency_ms = 1.234` (example — this is the geometric mean across all 7 benchmarks)
   - `metrics["score"] = 1.0 / 1.234 = 0.8104`
   - `metrics["score_name"] = "inv_latency_ms"`

## 11. Summary: What Determines the Final Score

For **GPUMode TriMul**:
- **Correctness gate:** All 18 test specs must pass (within `rtol=2e-2, atol=2e-2`) before any timing
- **Performance metric:** Each of the 7 benchmark specs is independently timed (CUDA events, convergence-based). The reported `latency_ms` is the **geometric mean** of all 7 per-benchmark mean latencies. This ensures the kernel is evaluated across diverse shapes (seqlen 256–1024), dimensions (128, 384), batch sizes (1–2), and distributions (normal, cauchy).
- **Score:** `1.0 / latency_ms` (higher is better = faster kernel)

For **FlashInfer-Bench**:
- **Correctness gate:** Output must match reference within `rtol=1e-2, atol=1e-2` per workload
- **Performance metric:** Mean latency across selected workloads (with warmup + multi-trial averaging)
- **Score:** `mean_vs_baseline_factor` (if baseline configured) or `speedup_factor` or `1.0 / latency_ms`

## 12. Cross-System Comparison: cudeepy-Style Benchmarking

K-Search's default evaluation uses per-iteration CUDA event timing with `torch.cuda.synchronize()` between each call. The cudeepy system uses batch CUDA event timing (single start event, N iterations, single end event) which avoids per-iteration sync overhead and more closely reflects real throughput.

A task-agnostic benchmark framework enables fair comparison between K-Search and cudeepy kernels:

- **`k_search/eval/benchmark.py`** — Generic benchmark library (timing, correctness, TFLOPS, reporting). No task-specific code.
- **`scripts/benchmark_cudeepy_style.py`** — CLI that loads cudeepy problem files or K-Search tasks.

### Usage: cudeepy Problems

```bash
# Benchmark a K-Search kernel on a cudeepy GEMM problem
python3 scripts/benchmark_cudeepy_style.py \
    --problem /path/to/cudeepy/problems/set_0/0_0_gemm4096x4096_fp16_acc32.py \
    --kernel path/to/submission.py

# Run all problems in a directory
python3 scripts/benchmark_cudeepy_style.py \
    --problem-dir /path/to/cudeepy/problems/set_0/ \
    --kernel path/to/submission.py

# From a K-Search solution JSON
python3 scripts/benchmark_cudeepy_style.py \
    --problem /path/to/problem.py \
    --solution-json path/to/solution.json
```

### Usage: TriMul (backward compatible)

```bash
python3 scripts/benchmark_cudeepy_style.py --task trimul --kernel path/to/submission.py
```

### Kernel Interface

For cudeepy problems, K-Search kernels use the same positional args as the reference `forward()`:

```python
def custom_kernel(a: torch.Tensor, b: torch.Tensor) -> torch.Tensor:
    ...
```

### What the Framework Reports

- **Correctness**: Element-wise comparison with auto-detected tolerances (FP16→atol=0.1, FP8→atol=0.5)
- **Batch CUDA event timing**: cudeepy methodology (no per-iteration sync overhead)
